# Routine: Root end-of-day self-improvement

- **Slug:** `root-end-of-day-self-improvement`
- **Owner:** Root Agent (the only routine Root owns; it concerns only Root itself)
- **Schedule:** daily, default 22:00 in the user's local time zone; set up on first contact by getting-started
- **Purpose:** Fires daily at the end of the user's day so Root reviews its own work, errors and corrections and proposes improvements.
- **Mode:** file audit only. The routine does not read the conversation; relay verification of Bot messages is completed by Root on its next interactive turn (result-relay step 5a). It writes only its report and Root's own end-of-day, delay-counter and reconciliation lines. If an installation has no routine, the same checks ride on the first turn of the next day (work-control steps 21, 24, 26 and 27).
- **Team-agnostic:** every team-specific input comes from Root's records (the work-queue's briefing delay counters and the reconciliation sources registered in domains.md), so a team added later is covered as soon as roster-management step 11 wires it in; the prompt never names a team.
- **Lifetime:** a daily routine. Like every one-off or temporary routine, it never deletes, disables or pauses itself or any other routine (bind-routine-via-owner step 16).

## Routine prompt

Schedule: daily at 22:00 in the user's local time zone (set on first contact).

End-of-day report and self-improvement review for Root Agent. Resolve <instance folder> via standing-workspace (verify the README Bot id matches yours; else stop). Write in the user's language.
Sources: (1) <instance folder>/daily-log/<date>.md. First list the daily-log folder with file sizes; report a 'record gap' (activity unknown) only when today's file is missing or 0 bytes, never 'no activity' and never from expectation or a failed search; a file with content is not a gap (standing-workspace daily-log and step 12); (2) do not try to read the conversation; the report rests on file records. Put 'Limit: report based on file records; relay verification of Bot messages is completed by Root on its next interactive turn' at the top; (3) dispatch-log.md, work-queue.md (including its briefing delay counters), domains.md (including each team's registered briefing and reconciliation sources), decisions.md, decisions-pending.md, and the registered team briefing files.
Write the report to <instance folder>/learning/<date>.md: a 3-5 line summary, then:
1) Task status: opened/closed/stuck today, and items idle 48h or more with their owner. Mark every open record past its `checkpoint-due` without newer evidence as `stalled?` with owner and proposed new date (work-control step 21). If the work-queue header date is older than its newest entry, or an open item sits below the archive heading, report it as a record defect. Team ledger reconciliation (work-control steps 24 and 26): for every active team, read only the sources registered for it in domains.md for entries dated today, list stop/restart/pause/rule-change entries, closures and recorded publishes that differ from work-queue or domains.md, and update Root's record with the source reference and date. If yesterday's report lacks this reconciliation or is missing, reconcile yesterday as well and mark it 'caught up'. A registered source that is missing or unreadable is a record defect of that team, with its path. Do not present a team's pending decisions from its register.
2) Questions and approvals pending from the user. A decision carried through three consecutive reports is presented as one highest-priority question (yes / no / defer to a date) plus a count of the rest (portfolio-status step 12). From Root's own decisions-pending.md only: mark decisions with a default whose 48 hours have passed as 'expired — recommendation applied on the next interactive turn', unanswered items past 48 hours as 're-ask once by card', and items past seven days as 'final card: close / defer / decide now'; list any 'your tasks' item whose one reminder is still due. Never extend a due date; do not list decisions in the report, the cards are shown on the next interactive turn (portfolio-status steps 13–14). Do not read the teams' registers for decisions. List one-off or temporary routines recorded as 'fired, awaiting closure decision' as questions for the user (bind-routine-via-owner step 16).
3) Rule compliance: unapproved deletion, unapproved external posting, unapproved applications or sends, commits with an identity other than the user's approved one or any Co-authored-by line for a Bot (each with evidence path). Run each check with an explicit date bound; a check command that errors is reported as 'not verified', never as zero findings. An external effect that no record or approval explains is listed as an open question for the user ('did you do this yourself?'), not as a violation (work-control step 23).
4) Briefings: for every team line in the work-queue's briefing delay counters (no hardcoded team names), a briefing for the period counts as received when the team's registered briefing file for the period exists (path and time) or dispatch-log has an inbound line from that team's owner in the period; dispatch-log decides only whether it was relayed. File present but no relay line = 'received, relay unverified', never 'not received'. Close the line for a received briefing; for a missing one start or advance it (first missing date, limit) so the status questions run on the next interactive turn (work-control step 25, blocker-escalation step 12). Lines marked closed, paused or excluded are not counted. An active team in work-queue or domains.md with no counter line, or with an open integration checklist item, is reported as 'not integrated' with the missing items (roster-management step 11). No quality judgment; only Lead-reported open issues.
5) Bot report relay check (mandatory, from file records only): list every message dispatch-log records as received from another Bot today, leaving out Bots the user excluded from tracking (they are also left out of the whole report), and match each with its relayed-to-user line and, where it contained a request, its answer line. Mark matched messages 'relayed (record)'. Mark every unmatched message, and any Bot message in the daily log missing from dispatch-log, 'relay unverified — Root completes on its next interactive turn'; never 'not relayed' (result-relay step 5a).
6) Cleanup: list files exceeding the recorded retention policy with path and sha256 for approval; NEVER delete.
7) Learning: today's errors and user corrections and which rule or skill each was written to; ready-to-apply proposals with old text, new text and reason; new skill drafts under learning/skill-proposals/<name>/SKILL.md only after an overlap check with existing skills. Every proposal for Root's description, skills or template must be generic: no personal names or handles, no bot or team names, no language or time-zone specifics, no instance paths or IDs; lessons specific to one user stay only in private records (daily log, learning report) and are not proposed for the template. Check each proposal for this ('is it generic?') and generalize it or mark it not for the template; a lesson about how one team or routine was wired in is checked against the team integration checklist (learning-loop step 10). Apply none.
8) Tomorrow's top 3.
9) Record step (mandatory, last): write one end-of-day line (time, report path, notification sent or not) to dispatch-log.md, update the work-queue header and its end-of-day line, and add a closing line to the day's daily log; then read each back. A failed, refused or mismatched write is listed in the report and is a reason to notify (work-control step 27, standing-workspace step 12).
On the user's weekly review day, add a weekly section. On that day also add a weekly review of Root's own decisions-pending.md: bulk-close proposals for closed or superseded items, decisions older than seven days (final card) and open 'your tasks' items, to be asked as cards (at most three per message) on the next interactive turn. Mark every active team, Lead or single Bot, with no weekly cleanup briefing in the last seven days as 'cleanup briefing missing'. Do not read the teams' registers for decisions or message the teams (portfolio-status step 14).
Notify the user only if there is a problem, question or approval (including a record gap, a failed record write or a team that is not integrated): a short summary plus the file path; otherwise save silently. 'Relay unverified' lines alone are not a reason to notify; Root completes them on its next interactive turn. No messages to other Bots, no deletion, no publishing, no profile or skill changes. This routine never deletes, disables or pauses itself or any other routine; a routine that should end is reported as a question for the user (bind-routine-via-owner step 16).
